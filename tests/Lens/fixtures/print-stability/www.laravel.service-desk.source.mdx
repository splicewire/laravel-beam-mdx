# Build a service desk

Build a team-owned request once, then follow it through the stock resource UI: a Member creates it, a different same-team Owner approves it, and usage and Inspection show the same committed approval. The example composes a declared resource, generated client, authorization and workflow; it adds no replacement dashboard.

## Follow one request

1. Sign in as the fresh preview's Member. Open **Service desk → Service requests → New**, enter a Title and choose Status, then Save.
2. Open the request's detail. ID, Title, Status and Approval use the read projection; the detail has no Save or Delete. Approval starts pending.
3. Sign in as a different authorized Owner on the same team and approve that request once.
4. Reload the detail, **Approval usage** and the request's **Inspection**. Quantity moves from zero to one; the same approval fact, actor, time and historical definition explain the change.

Use the preview chapter's native actors and selected-team setup. Keep their credentials private inside the disposable root. Usage here counts committed workflow facts; it does not bill a customer or debit a wallet.

The chapter also describes invalid values, forged ownership fields, foreign or removed membership, conflicts and a genuine source failure with Retry. Exercise those cases on the fresh host: an empty list, hidden button or disabled field does not establish server authorization.

## Read the declaration

`app/Data/ServiceRequestData.php` declares the `#[ParticleResource]`: its Eloquent `App\Models\ServiceRequest` backing, `ServiceRequestData` read DTO and `ServiceRequestInputData` input/edit DTO. The selected interactions are create, list and read-only detail. Editing and deletion are not enabled.

Input is Title, up to 200 characters, and Status, either `open` or `closed`. Output includes ID and Approval. Team and creator IDs come from server preparation, never from form input. `ServiceRequestTeam` and the resource scope check current selected-team membership.

The host supplies the model migration, resource realm placement, middleware, navigation and console mount. Attribute discovery removes a per-resource registry call; it does not create storage or grant access. The generic resource endpoint and the browser console remain separate mounts.

## Keep the client and UI on the same contract

The starter's generated routes and Data types describe the resource endpoint. Frame consumes the resource manifest, schema and matching transport to render its create/list/detail surfaces. The preview chapter owns generation and build instructions for its exact package inputs.

Create requests the write schema for Title and Status. Detail requests read purpose explicitly and pairs it with the read DTO's ID/Title/Status/Approval projection. A disabled legacy editor alone retains write purpose; it does not select a read schema. Failed read-schema loading offers Retry rather than silently switching to a write form.

Schema metadata and record access have different authority. In this example, an authenticated outsider may read global DTO metadata but cannot read another team's request. Server validation, live membership and record policy still apply to each operation. Generated TypeScript types do not replace runtime validation.
